# Типи сповіщень Cordova і створення технічних об’єктів

Цей документ фіксує перевірену поведінку legacy Cordova-клієнта та межі її перенесення у Mobile Facility App. У Cordova слово «тип» використовується для двох різних понять, які не можна змішувати: категорії сповіщення `QMART` та коду форми `STEUS`/`FORMNR`.

## 1. Категорії сповіщень (`QMART`)

| Код | Призначення | Поведінка |
| --- | --- | --- |
| `I1` | Технічне обслуговування та інспекції | Відкриті записи завантажуються у звичайний список сповіщень. Після локального закриття результат надсилається через `T0281`/`T0283`. |
| `I2` | Дефект | Створюється з негативного результату інспекції, якщо у користувача активований дозвіл `USER.I2 == "X"`. Це не окрема форма інспекції. |
| `I3` | Документна форма | Використовується спеціалізованими сценаріями інструктажу, електробезпеки, пожежних форм і підтвердження кваліфікації. Не є звичайним відкритим `I1` у списку. |

Поточний SwiftUI-клієнт імпортує лише відкриті `I1`. Це свідома межа: підтримка `I2` та `I3` має додаватися окремими вертикальними сценаріями, а не розширенням універсальної yes/no форми.

## 2. Коди форм (`STEUS` / `FORMNR`)

| Код | Legacy-маршрут | Призначення |
| --- | --- | --- |
| `TFM1` | `WartungsPlan` | План технічного обслуговування |
| `TFM2` | `Aufzugskontrolle` | Перевірка ліфта |
| `TFM3` | `Rundgang` | Обхідна перевірка |
| `TFM4` | `MasterDataForm` | Стаціонарні/приставні драбини |
| `TFM5` | `MasterDataForm` або `CreateNewForm` | Наявна або нова мобільна драбина |
| `TFM6` | `Aufzugskontrolle` | Система утримання дверей у відкритому положенні |
| `TFM7` | `MasterDataForm` або `CreateNewForm` | ПЗВ/підрозподільний щит |
| `TFM8` | `MasterDataForm` | Дахові системи |
| `TFM9` | `ElektrischenFormCreate` | Інструктаж/електрична форма |
| `TFMQ` | спеціалізований qualification flow | План `TFMQ_001`; не підтверджений як звичайний маршрут завантаженого сповіщення |

Карта вище описує можливості коду. Реальна доступність визначається синхронізованою конфігурацією SAP, зокрема `T0161`, тому відсутній у кеші шаблон не можна заміняти вигаданим production-шаблоном.

## 3. «Neuer TP» у Cordova

Кнопка відкриває два сценарії:

1. **Mobile Leiter** — обладнання типу `TFMLEITERN`, план типу `A`, legacy-план `00040015`, форма `TFM5`.
2. **Unterverteilung** — обладнання типу `TFMNSPV`, план типу `A`, форма `TFM7`; вибір батьків обмежений `TFMNSPV`/`TFMNSPVER`. У legacy-джерелі згадано план `TFM7_001`, однак production-кеш SAP може передати інший номер плану. Клієнт приймає лише кешований план `A` для `TFMNSPV` з позиціями `STEUS=TFM7`, зберігає фактичний `PLNNR` у чернетці та відправляє його без підміни.

Адресний контекст береться з кешованої ієрархії `T0272`. Створювані записи отримують стабільні локальні номери з префіксом `NEU`: `QMNUM` із 8-символьним суфіксом, `EQUNR` із 14-символьним суфіксом та окремий process ID. Вони створюються один раз перед постановкою у чергу й не змінюються при повторній синхронізації.

## 4. Контракт мобільної драбини (`TFM5`)

Форма вимагає матеріал, тип конструкції, виробника, додатну кількість щаблів, компанію-замовника, приміщення, позначення, адресний контекст і результат для кожного пункту. Заводський та інвентарний номери необов’язкові.

Результати зберігаються SAP-кодами `1`–`5`: справно, потрібне очищення, незначний дефект, значний дефект, відсутня. Дії мають коди `7`–`9`: потрібен ремонт, відремонтовано, виведено з експлуатації. Текст у UI локалізований, але transport ніколи не використовує локалізований текст як код.

| Таблиця | Вміст |
| --- | --- |
| `T0281` | Заголовок `I1`, `FORMNR=TFM5`, адреса, план, статус, дата та упакований `T_PLPOD` |
| `T0283` | Результат, необов’язкова дія, коментар кожної позиції та загальний статус `iBet`/`dem` |
| `T0266` | Нове обладнання `TFMLEITERN`, функціональне місце та клас `TFMMOBLEITER_*` |
| `T0282` | JPEG-документи, прив’язані до `...-9B`; клас `D_TFM_Dokumentation`, value list `TFM001` |

Максимум — 20 фотографій на одну форму. Фото завантажуються перед завершальним TO-post. Чернетка, ідентифікатори й файли видаляються лише після підтвердження SAP; при помилці вони залишаються для повторної спроби.

## 5. Офлайн-стани та demo

- Тимчасове збереження → `draft`.
- Закриття production-форми → `pendingSynchronization`.
- Підготовка TO → `synchronizing`.
- Помилка → `failed` із повторним використанням тих самих `NEU`-ідентифікаторів.
- Підтвердження SAP → видалення локальної роботи та фото; створений об’єкт повертається наступним FROM-refresh.
- У demo всі збереження залишаються локальними `draft`; production provider, SQLite SAP і мережевий sync не створюються та не викликаються.

## 6. Рекомендована черговість міграції

1. `TFM5` Mobile Ladder — контракт створення та SwiftUI reference повні й перевіряються тестами.
2. Спеціалізовані форми перегляду наявних `I1` (`TFM1`–`TFM8`) замість універсальної yes/no форми.
3. `I2` defect creation із перевіреною авторизацією та SAP-мапінгом.
4. `I3`/`TFM9`/`TFMQ` документні сценарії з PDF-паритетом.
5. `TFM7` Subdistribution після підтвердження production-мапінгу та правил вибору батьківського об’єкта.

До завершення пункту 5 підрозподільний щит залишається видимим у меню «Neuer TP», але позначеним як недоступний.
